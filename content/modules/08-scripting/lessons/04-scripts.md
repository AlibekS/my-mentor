# Скрипты: файл, аргументы, exit-коды, строгий режим

## Анатомия скрипта

```bash
#!/usr/bin/env bash
# check_service.sh — проверка сервиса и его порта
set -euo pipefail

SERVICE=${1:?Использование: $0 <service>}   # $1 обязателен
PORT=${2:-80}

if ! systemctl is-active -q "$SERVICE"; then
  echo "FAIL: $SERVICE не active"
  exit 1
fi
echo "OK: $SERVICE"
```

- **Shebang** `#!/usr/bin/env bash` — каким интерпретатором выполнять.
- **Аргументы**: `$1`, `$2`… — позиционные; `$#` — сколько; `$@` — все; `$0` — имя скрипта.
- **exit N** — код выхода скрипта: 0 — ок; другое — сигнал cron/мониторингу/CI, что проверка не прошла.

## Запуск

```bash
nano check.sh            # в тренажёре откроется редактор (Ctrl+S — сохранить)
chmod +x check.sh        # право на выполнение
./check.sh nginx         # запуск (нужен x)
bash check.sh nginx      # запуск без x
bash -n check.sh         # только проверить синтаксис
```

`./check.sh: Permission denied` (код 126) — забыт `chmod +x`.

## Строгий режим: set -euo pipefail

- `-e` — выйти при первой ошибке (а не идти дальше с битыми данными);
- `-u` — ошибка при обращении к неопределённой переменной (опечатка `$FIEL` не превратится в пустую строку);
- `-o pipefail` — код пайпа = код первой упавшей команды, а не последней.

> Классика: `rm -rf "$DIR/"*` при пустом `$DIR` без `set -u` превращается в `rm -rf /*`.

## Функции

```bash
check_http() {
  local url=$1
  local code
  code=$(curl -s -o /dev/null -w "%{http_code}" "$url")
  [ "$code" = "200" ]
}
check_http https://shop.kz/health && echo OK || echo FAIL
```

## Когда пора взять Python

Bash хорош для склейки команд. Если появились JSON-структуры, сложная логика, повторные попытки с бэкоффом, API-клиенты — пиши на Python (`requests`, `json`). L3 в вакансиях обычно ждут оба: bash для однострочников, Python для инструментов.

## Как это выглядит на реальной работе L3

Повторяющийся шаг runbook («проверить 5 вещей после рестарта») L3 оформляет скриптом с понятным выводом `OK/FAIL` и кодом выхода — его можно дать L2 и повесить в cron/мониторинг.

## Типичные ошибки

- Нет shebang и `chmod +x`.
- Скрипт всегда возвращает 0 — мониторинг не узнает о проблеме.
- Без `set -u`/кавычек — опасные `rm` с пустыми переменными.
