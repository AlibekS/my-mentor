# Доступность: ping и traceroute

## ping

```
ping -c 4 db-prod-01
```

Отправляет ICMP echo и показывает время ответа (RTT) и потери (`packet loss`). Всегда указывай `-c` — иначе пинг бесконечный (Ctrl+C).

Что читать:
- `0% packet loss`, стабильное время — сеть до узла в порядке;
- `100% packet loss` — узел недоступен **или ICMP запрещён фаерволом** (в облаках это часто: AWS security group по умолчанию режет ICMP);
- рост времени (10 мс → 400 мс) и потери 5–20% — перегрузка канала/узла.

> **ping не отвечает ≠ сервис недоступен.** Проверяй сам сервис: `curl`, `nc -vz host port`. И наоборот: ping есть — а порт 443 закрыт.

## traceroute

```
traceroute api.partner.com
```

Показывает **путь по хопам** (маршрутизаторам) и задержку до каждого. `* * *` — хоп не ответил (часто норма — он просто не отвечает на такие пакеты). Важна точка, **после которой** ответов больше нет, или где резко растёт задержка.

Вариант — `mtr`: ping + traceroute в реальном времени, удобен, чтобы показать провайдеру потери на конкретном хопе.

## Как это использует L3

Партнёрский API тормозит только у части клиентов. Ты: `ping` — 0% потерь, но 180 мс вместо 20. `traceroute` — задержка растёт на хопе транзитного провайдера. Это не наш код: эскалация к сетевой команде/провайдеру с трассой в тикете.

## Типичные ошибки

- Делать вывод «сервер лежит» по одному отсутствию ping.
- Пинговать имя и не замечать, что оно резолвится не в тот IP (смотри строку `PING host (IP)`).
- Читать `* * *` в середине трассы как поломку.
