# REST API и JSON

В SaaS-поддержке половина обращений — про интеграции: «webhook не приходит», «API отдаёт 401», «в ответе пустой список». L3 должен уметь сам сделать запрос к API и разобрать JSON.

## REST в двух словах

- **Ресурсы** по URL: `/v1/orders`, `/v1/orders/1042`.
- **Методы**: `GET` — прочитать, `POST` — создать, `PUT/PATCH` — изменить, `DELETE` — удалить.
- **Формат** — JSON; заголовок `Content-Type: application/json`.
- **Аутентификация** — чаще всего токен в заголовке: `Authorization: Bearer <token>` (OAuth 2.0 / API key).

```
curl -s -H "Authorization: Bearer $TOKEN" https://api.shop.kz/v1/orders?status=failed
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"order_id": 1042, "reason": "duplicate"}' https://api.shop.kz/v1/refunds
```

> Токен — секрет. В тикеты и чаты — никогда; в команде — через переменную (`$TOKEN`), чтобы не осел в истории и скриншотах.

## JSON и jq

```json
{"items": [{"id": "o1", "status": "paid", "total": 10}, {"id": "o2", "status": "failed", "total": 25}], "next": null}
```

`jq` — grep/awk для JSON:

```
jq '.'                                   # красиво отформатировать
jq '.items | length'                     # сколько элементов
jq '.items[0]'                           # первый
jq -r '.items[].id'                      # все id, без кавычек (-r)
jq '.items[] | select(.status == "failed")'
jq -c '.items[] | {id, total}'           # только нужные поля, компактно
jq '[.items[].total] | add'              # сумма
```

## Коды, характерные для API

- **400** — невалидный JSON/параметры (тело ответа обычно объясняет, какое поле).
- **401** — нет токена или он истёк. **403** — токен есть, но нет scope/прав.
- **404** — ресурса нет (или неверная версия API в URL).
- **409** — конфликт (уже существует, версия устарела).
- **422** — данные понятны, но не проходят бизнес-валидацию.
- **429** — rate limit: смотри `Retry-After`, лимиты в заголовках `X-RateLimit-*`.

## Как это выглядит на реальной работе L3

Клиент: «через API не видим заказы за вчера». Ты повторяешь запрос **его** токеном (из безопасного хранилища, с разрешения) — получаешь 200 и `"items": []`. Тот же запрос с параметром `?created_after=` в UTC — заказы есть. Клиент передавал дату в локальном времени без зоны. Решение — объяснение + ссылка на документацию, без эскалации в разработку.

## Типичные ошибки

- Вставлять токен прямо в команду и потом в тикет.
- Не смотреть тело ответа 4xx — там обычно написана причина.
- Путать «пустой список» (200) и «нет доступа» (403).
