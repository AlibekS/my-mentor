# Интерфейсы и порты: ip, ss

У тебя CCNA — модель OSI и TCP/IP ты знаешь. L3 нужна прикладная часть: **кто на сервере слушает какой порт и на каком адресе**.

## ip — адреса и маршруты

```
ip a          # интерфейсы и IP (ip addr)
ip r          # маршруты; default via ... — шлюз
hostname -I   # только IP-адреса
```

`ifconfig` и `netstat` из пакета net-tools — устаревшие, на свежих системах их может не быть.

## ss — сокеты

```
ss -tulpn
```

- `t` — TCP, `u` — UDP, `l` — только слушающие (LISTEN), `p` — процесс (чужие — через `sudo`), `n` — числа вместо имён (`:443`, а не `:https`).

```
Netid State  Local Address:Port   Process
tcp   LISTEN 0.0.0.0:80           users:(("nginx",pid=1101,fd=6))
tcp   LISTEN 127.0.0.1:5432       users:(("postgres",pid=901,fd=5))
tcp   LISTEN 127.0.0.1:8080       users:(("java",pid=2240,fd=9))
```

## 0.0.0.0 против 127.0.0.1 — классика инцидентов

| Слушает на | Кто может подключиться |
|---|---|
| `0.0.0.0:80` (или `*:80`, `[::]:80`) | со всех интерфейсов — снаружи тоже |
| `127.0.0.1:8080` | **только с этого же сервера** |
| `10.0.1.15:9090` | только через этот интерфейс |

«Сервис запущен, порт открыт, а снаружи не подключиться» — частая причина: приложение слушает `127.0.0.1`. Вторая — фаервол (security group, iptables/nftables).

## Полезные порты

22 SSH · 53 DNS · 80 HTTP · 443 HTTPS · 3306 MySQL · 5432 PostgreSQL · 6379 Redis · 9090 Prometheus · 9200 Elasticsearch · 8080/8081 — часто приложения за nginx.

## Как это выглядит на реальной работе L3

Новый сервис мониторинга не видит метрики приложения. Ты: `sudo ss -tulpn | grep 9100` → `127.0.0.1:9100`. Exporter слушает только localhost, а Prometheus стучится с другого хоста. Фикс — флаг `--web.listen-address=0.0.0.0:9100` + правило фаервола только для сервера мониторинга.

## Типичные ошибки

- `ss -tulpn` без `sudo` — колонка Process пустая для чужих процессов.
- Открывать сервис на `0.0.0.0` «чтобы заработало» — БД и Redis не должны смотреть в интернет.
- Забыть про UDP (DNS, syslog) — `ss -tlpn` его не покажет.
