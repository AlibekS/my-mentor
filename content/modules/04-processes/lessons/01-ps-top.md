# Процессы: ps и top

Процесс — это запущенная программа с номером **PID**. Когда «всё тормозит» или «сервис съел память», L3 первым делом смотрит на процессы.

## ps aux — снимок всех процессов

```
$ ps aux
USER        PID %CPU %MEM     VSZ    RSS TTY  STAT START   TIME COMMAND
root          1  0.0  0.1  168000  12400 ?    Ss   Oct12   0:41 /sbin/init
shop       2240  3.5  9.8 4100000 790000 ?    Ssl  Nov03  58:31 /usr/bin/java -jar /opt/shop/shop.jar
```

| Колонка | Смысл |
|---|---|
| `USER` | от чьего имени работает |
| `PID` | идентификатор процесса |
| `%CPU`, `%MEM` | доля процессора и памяти |
| `VSZ` | виртуальная память (КБ) — «заказано», часто огромное и неважное |
| `RSS` | **резидентная** память (КБ) — реально занято в RAM |
| `STAT` | состояние: `R` работает, `S` спит, `D` ждёт диск/сеть (не прерывается), `Z` зомби, `T` остановлен |
| `TIME` | сколько процессорного времени израсходовано всего |
| `COMMAND` | команда запуска с аргументами (видно `-Xmx2g`, путь к jar, конфиг) |

`ps -ef` — тот же список в другом формате (с PPID — родителем).

## Найти и отсортировать

```
ps aux | grep java                 # найти процесс
pgrep -a nginx                     # PID и командная строка по имени
ps aux --sort=-%cpu | head -5      # топ по CPU
ps aux --sort=-%mem | head -5      # топ по памяти
ps aux | sort -k4 -rn | head -5    # то же через sort: 4-я колонка = %MEM
```

> `ps aux | grep java` покажет и сам `grep java`. Обход: `grep [j]ava` или `pgrep`.

## top — в реальном времени

```
top
```

Сверху: uptime и **load average**, сколько задач, `%Cpu(s)` (`us` — пользовательский код, `sy` — ядро, `wa` — **ожидание диска**, `id` — простой), память и swap. Ниже — процессы, по умолчанию сортировка по CPU.

Клавиши: `P` — по CPU, `M` — по памяти, `k` — убить процесс, `1` — по ядрам, `q` — выход. Популярная альтернатива — `htop`.

> В тренажёре `top` показывает статичный снимок.

## Как это выглядит на реальной работе L3

Алерт: CPU 95% на app-02. Ты: `top` → видишь `java` с 380% CPU (4 ядра заняты), `ps -o pid,etime,args -p <PID>` — запущен 3 часа назад, после деплоя. Снимаешь thread dump для разработчиков, а если сервис деградирует — перезапускаешь через systemd и открываешь проблему.

## Типичные ошибки

- Смотреть на `VSZ` и паниковать: «java занимает 4 ГБ!». Важен `RSS`.
- Сортировать `sort -k3 -r` без `-n` — строковая сортировка.
- Видеть 100% CPU у процесса на 8-ядерной машине и думать, что сервер загружен полностью (это одно ядро из восьми).
