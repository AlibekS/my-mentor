# Runbook и база знаний

Инцидент, разобранный один раз, должен решаться в следующий раз **быстрее и без L3**. Для этого — runbook и статья в базу знаний (KB).

## Runbook (регламент)

Пошаговая инструкция для **дежурного**, который видит алерт в 3 ночи. Пишется так, чтобы её мог выполнить L2 без глубокого знания системы.

```
# Runbook: PaymentsDbPoolSaturated
## Симптомы
Алерт PaymentsDbPoolSaturated; рост 5xx у payments/checkout; p99 ~30 с.
## Диагностика
1. Дашборд «Shop — RED»: занятость пула db_pool_connections_in_use.
2. Кто держит соединения: SELECT pid, application_name, state, now()-query_start AS dur, left(query,80)
   FROM pg_stat_activity WHERE datname='payments' ORDER BY dur DESC LIMIT 20;
3. Логи payments: service:payments AND level:warn — медленные запросы, фоновые задачи.
## Митигация
- Если соединения держит фоновая задача (reconcile-report): остановить job → kubectl delete job …
- Если всплеск трафика: kubectl scale deployment/payments --replicas=6 (было 4; у каждого пода свой пул — сверь сумму с max_connections БД).
## Проверка
Пул < 70%, доля 5xx < 1% в течение 10 минут.
## Эскалация
Не помогло за 15 мин → @payments-oncall (PagerDuty), SEV2.
```

Принципы: **конкретные команды и запросы**, проверка результата после каждого шага, ясный критерий «когда эскалировать», ссылка из алерта прямо на runbook.

## Статья в базу знаний (KB)

Для поддержки и клиентов: известная проблема и что делать.

```
Заголовок: Оплата падает с ошибкой «Payment failed, try again later»
Симптомы: …   Причина: …   Решение / обход: …   Статус: исправлено в 3.7.1
```

Связь с ITIL: KB-статья о проблеме с обходом — это **known error**.

## Автоматизация

Повторяющийся шаг runbook — кандидат на автоматизацию (скрипт, кнопка в ChatOps, авто-ремедиация). Но сначала — понятный ручной runbook.

## Как это выглядит на реальной работе L3

После каждого инцидента L3 проверяет: был ли runbook? помог ли? Если нет — пишет или обновляет его в рамках action items. Хороший показатель зрелости поддержки — доля алертов со ссылкой на работающий runbook.

## Типичные ошибки

- Runbook из общих слов: «проверить базу данных».
- Нет критерия успеха и эскалации.
- Runbook лежит в личной папке, а не по ссылке из алерта.
