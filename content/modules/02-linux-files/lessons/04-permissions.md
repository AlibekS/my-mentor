# Права и владельцы: «Permission denied»

`Permission denied` — одна из самых частых причин «сервис не стартует после деплоя». L3 должен за минуту понять, **кто** пытается прочитать файл и **почему не может**.

## Читаем ls -l

```
-rw-r----- 1 root www-data 512 Nov  4 10:00 /etc/shop/db.conf
│└┬┘└┬┘└┬┘   └┬─┘ └──┬───┘
│ │  │  │     │      └ группа-владелец
│ │  │  │     └ пользователь-владелец
│ │  │  └ права остальных (others): ---
│ │  └ права группы (group): r--
│ └ права владельца (user): rw-
└ тип: - файл, d каталог, l ссылка
```

| Символ | Для файла | Для каталога |
|---|---|---|
| `r` (4) | читать содержимое | видеть список файлов |
| `w` (2) | изменять | создавать/удалять файлы внутри |
| `x` (1) | запускать | **входить** (`cd`) и обращаться к файлам внутри |

## Числовая запись

Каждая тройка — сумма: `r=4, w=2, x=1`.

- `644` = `rw-r--r--` — обычный файл.
- `640` = `rw-r-----` — конфиг с секретами: владелец пишет, группа читает, остальные — ничего.
- `600` = `rw-------` — ключи, пароли.
- `755` = `rwxr-xr-x` — каталоги, скрипты.
- `777` — **всем всё**. На проде почти всегда ошибка безопасности.

## Как Linux проверяет доступ

1. Ты владелец? → смотрим первую тройку.
2. Нет, но ты в группе файла? → вторая тройка.
3. Иначе → третья.

Плюс: чтобы прочитать `/etc/shop/db.conf`, нужен `x` на **все каталоги по пути** (`/etc`, `/etc/shop`).

## Меняем права и владельцев

```
chmod 640 db.conf          # числом
chmod u+x deploy.sh        # добавить владельцу запуск
chmod g-w,o-r file         # убрать
sudo chown www-data:www-data /var/www/uploads   # владелец и группа
sudo chown -R app:app /opt/app                  # рекурсивно
```

`chown` (и чужой `chmod`) — только через `sudo`. `id` покажет, в каких ты группах.

## sudo

`sudo команда` — выполнить от root. Правило L3: **sudo осознанно и точечно**, а не `sudo su` на весь день.

## Как это выглядит на реальной работе L3

После деплоя `app.service` в статусе failed. В журнале: `open /etc/shop/db.conf: permission denied`. Смотришь `ls -l`: файл принадлежит `root:root` с `600`, а сервис работает от пользователя `shop`. Деплой-скрипт скопировал конфиг от root. Фикс: `sudo chown root:shop /etc/shop/db.conf && sudo chmod 640 /etc/shop/db.conf`, рестарт — и задача в бэклог: починить деплой-скрипт.

## Типичные ошибки

- «Починить» через `chmod 777` — открыть секреты всему серверу.
- Забыть про права на каталог (`x`), когда у файла права в порядке.
- `chown -R` не на тот каталог (например, `/` вместо `./`).
