# Поиск аномалий в данных

L3 часто ищет не «одну запись», а **закономерность**: дубли, зависшие статусы, расхождения сумм, всплески во времени. Это комбинация того, что ты уже знаешь.

## 1. Дубли

```sql
SELECT order_id, COUNT(*) AS n
FROM payments
WHERE status = 'succeeded'
GROUP BY order_id
HAVING COUNT(*) > 1;
```

Дубликат = одинаковый «бизнес-ключ» (заказ, email, внешний id), встречающийся больше одного раза там, где должен быть один.

## 2. Зависшие статусы (рассинхрон)

«Заказ оплачен, но висит в pending» — статусы двух таблиц противоречат друг другу:

```sql
SELECT o.id, o.status, p.status AS payment_status, p.created_at
FROM orders o
JOIN payments p ON p.order_id = o.id
WHERE o.status = 'pending' AND p.status = 'succeeded';
```

Типичная причина — потерянный **webhook** от платёжного провайдера.

## 3. Расхождение сумм (подзапрос / CTE)

```sql
WITH items_sum AS (
  SELECT order_id, ROUND(SUM(qty * price), 2) AS calc
  FROM order_items GROUP BY order_id
)
SELECT o.id, o.total, s.calc
FROM orders o JOIN items_sum s ON s.order_id = o.id
WHERE ABS(o.total - s.calc) > 0.01;
```

`WITH … AS (…)` — **CTE**, именованный подзапрос: читается сверху вниз, как пайп. Сравниваем числа с допуском (`ABS(...) > 0.01`) — деньги в REAL/float могут дать `0.30000000000000004`.

## 4. Всплески во времени

```sql
SELECT strftime('%Y-%m-%d %H:00', created_at) AS hour, status, COUNT(*)
FROM payments GROUP BY hour, status ORDER BY hour;
```

Сравни «как обычно» и «во время инцидента» — так находится окно и масштаб.

## Как это выглядит на реальной работе L3

Три тикета за час: «списали дважды». Ты ищешь дубли платежей → находишь несколько заказов с двумя успешными списаниями — все через один провайдер и в одном окне (14:05–15:05). Это уже не «жалобы клиентов», а инцидент с измеримым impact: N клиентов, сумма к возврату, окно, провайдер. С этим идут в эскалацию и к финансам.

## Типичные ошибки

- Считать дубли без фильтра по статусу: неуспешная попытка + успешная — это не двойное списание.
- Сравнивать деньги через `=` во float.
- Делать выводы по одному примеру — всегда считай масштаб запросом.
