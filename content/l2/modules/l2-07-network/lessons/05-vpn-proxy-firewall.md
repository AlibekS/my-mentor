# VPN, прокси и фаервол глазами пользователя: timeout, refused или NXDOMAIN

Клиенты SaaS сидят в корпоративных сетях: VPN, прокси, фаерволы. Наш сервис может работать идеально, а у сотрудника конкретной компании — «не открывается». L2 не настраивает сеть клиента, но **по тексту ошибки** понимает, где искать, и говорит клиенту, что передать его IT-отделу.

## Цепочка «открыть сайт» — и где она рвётся

```
1. DNS: имя → IP       ──✗──▶  NXDOMAIN / Could not resolve host
2. TCP: соединиться    ──✗──▶  Connection timed out  (ответа нет)
                       ──✗──▶  Connection refused    (быстрый отказ)
3. TLS + HTTP          ──✗──▶  ошибки сертификата, 4xx/5xx (это уже не сеть)
```

## Шпаргалка: три ошибки

| Ошибка | Как выглядит | Что значит | Частые причины у корпоративного клиента |
|---|---|---|---|
| **NXDOMAIN** | `curl: (6) Could not resolve host`, `DNS_PROBE_FINISHED_NXDOMAIN` | имя не нашлось в DNS | опечатка; **внутреннее имя** компании (`*.corp`, `*.internal`) видно только через **VPN**; домен не настроен |
| **Timeout** | `curl: (28) … Timeout was reached`, `ERR_CONNECTION_TIMED_OUT`, `ETIMEDOUT` | пакеты ушли и **пропали** — ответа нет | **фаервол** молча режет (часто только определённые сайты/порты); узел выключен; VPN «заворачивает» трафик не туда |
| **Refused** | `curl: (7) … Couldn't connect`, `ERR_CONNECTION_REFUSED`, `ECONNREFUSED` | узел **ответил отказом** — на порту никто не слушает | сервис не запущен; неверный порт; иногда фаервол настроен отвечать отказом |

Главная подсказка — **время**: refused приходит мгновенно, timeout — после ожидания (10–30 с и больше).

## VPN

**VPN** — защищённый «туннель» из ноутбука в сеть компании. С включённым VPN сотрудник видит внутренние сайты (`wiki.acme.corp`) и выходит в интернет через офис. Типичные тикеты:

- «Из дома не открывается внутренний портал» → имя внутреннее → NXDOMAIN без VPN. Решение: подключить VPN.
- «С VPN не открывается ваш сервис, без VPN — открывается» → офисная сеть или фаервол компании блокирует наш адрес. Решение: IT клиента добавляет наш домен/IP в разрешённые.

## Прокси

**Прокси** — посредник: все запросы в интернет идут через сервер компании, который проверяет и фильтрует их. На Linux/Mac его обычно задают переменными окружения:

```
env | grep -i proxy
HTTPS_PROXY=http://proxy.acme.corp:3128
NO_PROXY=localhost,.acme.corp
```

`HTTPS_PROXY` — через какой прокси ходить, `NO_PROXY` — для каких адресов прокси не нужен. В Windows и браузерах прокси настраивается в системных настройках. Прокси может блокировать отдельные сайты (часто — сервисы загрузки файлов), большие файлы или WebSocket.

## Фаервол

**Фаервол** (межсетевой экран, firewall) — правила «что пропускать». Корпоративные фаерволы часто работают по **разрешённому списку (allowlist)**: наружу можно только на перечисленные адреса. Если наш сервис сменил IP, а у клиента в allowlist старый — у всей компании «timeout», а у остальных клиентов всё работает. (Это сюжет босса модуля.)

## Быстрый тест «моя сеть или ваш сервис?»

Попросить клиента открыть сервис **с мобильного интернета** (раздать с телефона) или из дома. Работает там — проблема в корпоративной сети, и решать её будет IT клиента. Не работает нигде — смотрим на нашей стороне.

## Как это выглядит в тикете

> Загрузка файлов у ACME зависает: `uploads.shopflow.io` → timeout, при этом `app.shopflow.io` отвечает 200. Трафик идёт через прокси `proxy.acme.corp:3128`. Похоже, корпоративный прокси/фаервол блокирует uploads. Попросили IT клиента разрешить `*.shopflow.io`, проверили с мобильного интернета — загрузка работает. Эскалация в L3 не нужна.

## 🇬🇧 English corner

- *Are you connected to a VPN?* — Вы подключены к VPN?
- *Does it work from your mobile network or from home?* — Работает ли с мобильного интернета или из дома?
- *Please ask your IT team to allow \*.shopflow.io in the firewall.* — Попросите ваш IT-отдел разрешить \*.shopflow.io в фаерволе.
- *Do you use a proxy server?* — Вы пользуетесь прокси-сервером?
- *allowlist* — список разрешённых адресов; *blocked* — заблокировано.
