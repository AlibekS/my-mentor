# Воспроизведение и сбор данных

Самый частый тикет в поддержке звучит так: **«У меня не работает»**. Что не работает? У кого? Когда? Что человек нажимал? Без ответов на эти вопросы ни L2, ни L3 ничего не найдут. Поэтому главный навык L2 — **собрать факты** и **воспроизвести (reproduce)** проблему, то есть повторить её самому.

## Зачем воспроизводить

Если ты смог повторить ошибку — половина работы сделана:
- ты точно знаешь, **что** ломается (а не пересказ клиента);
- ты можешь проверить, **у всех ли** так или только у этого клиента;
- после исправления ты сможешь **проверить фикс** теми же шагами.

Если повторить не получилось — это тоже ценный факт: значит, дело в чём-то, что отличается у клиента (его настройки, браузер, данные, сеть).

## Пять вопросов: что собрать у клиента

| Вопрос | Что нужно | Пример |
|---|---|---|
| **Кто?** | магазин (store id), email пользователя, роль | `tbilisi-wine`, nino@tbilisiwine.ge, владелец |
| **Что?** | шаги и **ожидаемый результат** против **фактического** | «Нажимаю «Вернуть деньги» → жду возврат → вижу «Что-то пошло не так»» |
| **Когда?** | время **с часовым поясом**, один раз или постоянно | «около 14:14 по Тбилиси, повторяется каждый раз» |
| **Где?** | браузер и версия, устройство, ОС, страница (URL) | Chrome 130, Windows 11, страница заказа #5521 |
| **Доказательства** | точный текст ошибки, скриншот, **request id** | «Request ID: req_8f2c41» в окне ошибки |

### Ожидаемый и фактический результат

Это пара, которую L3 ценит больше всего:
- **Ожидаемый результат (expected result):** «деньги возвращаются покупателю, статус заказа — Refunded».
- **Фактический результат (actual result):** «появляется окно «Что-то пошло не так», статус не меняется».

### Request id — золотой билет

Многие SaaS-продукты показывают в окне ошибки **request id** (идентификатор запроса) — уникальную строку вроде `req_8f2c41`. Каждый запрос к серверу получает свой id, и он записывается во все логи. Если клиент прислал request id, ты найдёшь в логах **именно его запрос** за секунды, а не будешь угадывать среди миллионов строк.

## Шаги воспроизведения (steps to reproduce)

Записывай так, чтобы любой человек повторил ошибку без вопросов:

```
Steps to reproduce:
1. Войти в админку магазина tbilisi-wine под владельцем.
2. Открыть Заказы → заказ #5521.
3. Нажать «Вернуть деньги», ввести сумму 120 GEL, подтвердить.
Expected: возврат создан, статус Refunded.
Actual: окно «Что-то пошло не так», request id req_8f2c41.
```

Маленькие шаги, конкретные данные (какой магазин, какой заказ, какая сумма). «Попробуйте сделать возврат» — плохо: какой заказ? какая сумма?

## Один вопрос — одно письмо

Клиент не должен отвечать пять раз. Если данных не хватает, **спроси всё сразу, списком**, вежливо и объясняя зачем:

> Здравствуйте, Нино! Спасибо, что написали. Чтобы быстро разобраться, пришлите, пожалуйста:
> 1. Номер заказа и сумму возврата.
> 2. Примерное время, когда появилась ошибка (и ваш часовой пояс).
> 3. Скриншот окна с ошибкой — в нём есть строка «Request ID».
> 4. Браузер и устройство (например, Chrome на Windows).
>
> С уважением, Алибек, ShopFlow Support

После такого письма тикет уходит в **Pending** — ждём клиента.

## Время в логах — в UTC

Клиент говорит «около 14:14 по Тбилиси». Тбилиси — UTC+4, значит в логах искать `10:14` (14:14 − 4 часа). Логи серверов почти всегда пишут время в UTC — с буквой `Z` на конце: `2026-11-04T10:14:02Z` (Z = «Zulu time» = UTC).

## Терминал: от request id к строке лога

```
grep -i "request" ~/tickets/ZD-2301.txt          # найти в тикете строку с request id
grep req_8f2c41 /var/log/shopflow/app.log         # все строки лога этого запроса
```

Флаг `-i` у grep — «не важно, большие или маленькие буквы» (ignore case): найдёт и `Request`, и `request`.

Строка лога выглядит так:

```
2026-11-04T10:14:02Z ERROR request_id=req_8f2c41 store=tbilisi-wine status=422 error=REFUND_EXCEEDS_CAPTURED
```

Читаем слева направо: **время** (UTC) → **уровень** (ERROR — ошибка) → **request id** → **магазин** → **HTTP-статус** → **код ошибки**. Код ошибки обычно понятен и человеку: `REFUND_EXCEEDS_CAPTURED` = «возврат больше, чем было списано».

## Как это выглядит в тикете

Иногда сбор данных сразу даёт решение. В примере выше клиент пытался вернуть 120 GEL, а покупатель заплатил 95 GEL — система правильно отказала. Это не баг, эскалировать нечего: L2 объясняет клиенту, в чём дело, и тикет решён. А в internal note остаются факты: request id, строка лога, вывод.

## 🇬🇧 English corner

Термины: *steps to reproduce* — шаги воспроизведения, *expected result* — ожидаемый результат, *actual result* — фактический результат, *request id* — идентификатор запроса, *screenshot* — скриншот.

- *Could you describe the steps?* — Опишите, пожалуйста, шаги.
- *What time did it happen, and in which time zone?* — Во сколько это случилось и в каком часовом поясе?
- *Could you send me a screenshot of the error?* — Пришлите, пожалуйста, скриншот ошибки.
- *Which browser do you use?* — Каким браузером вы пользуетесь?
- *I was able to reproduce the issue.* — Мне удалось воспроизвести проблему.
