# Network: медленный запрос, Timing и TTFB

Жалоба «всё тормозит» — одна из самых частых. Клиенту кажется, что «медленный весь сайт». В Network почти всегда видно, что медленный **один-два запроса**, и видно, **где** уходит время: в сети или на сервере.

## Шаг 1. Найти самый долгий запрос

Колонка **Time** — сколько длился запрос. Кликни по заголовку колонки, чтобы отсортировать (в тренажёре просто пробеги глазами). Полезно смотреть и на **Waterfall** — длинная полоса сразу бросается в глаза.

```
Name        Status  Method  Type   Time
me          200     GET     fetch  95 ms
search      200     POST    fetch  8.42 s   ← вот он
stats       200     GET     fetch  240 ms
```

Ориентиры для API: до 300 мс — быстро, 1–2 с — заметно, больше 5 с — клиент считает, что «сайт висит».

## Шаг 2. Timing — из чего сложилось время

Клик по запросу → вкладка **Timing**:

| Этап | Что происходит | Если долго — где проблема |
|---|---|---|
| **DNS Lookup** | поиск IP по имени сайта | DNS у клиента или провайдера |
| **Initial connection** | установка TCP-соединения | сеть, VPN, прокси, расстояние |
| **SSL** | «рукопожатие» шифрования (TLS) | сеть, перегруженный сервер |
| **Waiting for server response (TTFB)** | сервер **думает** — от отправки запроса до первого байта ответа | **сервер**: медленный запрос в БД, тяжёлый отчёт |
| **Content Download** | скачивание ответа | большой ответ или медленный интернет |

**TTFB** (Time To First Byte, «время до первого байта») — главный показатель для поддержки. Большой TTFB = проблема на нашей стороне (сервер, база данных), сеть клиента тут ни при чём. Большие DNS/Connect/SSL = проблема ближе к клиенту (его сеть, VPN, прокси).

## Шаг 3. Что было в запросе и что ответил сервер

- **Payload** — что отправил браузер. Для поиска это фильтры: статусы, даты, номер страницы.
- **Response** — что ответил сервер. Иногда сервер сам подсказывает причину: `"warning": "Slow query…"`.

Частая история SaaS: клиент выбрал период «за всё время» или убрал фильтры — сервер честно перебирает миллионы строк. Решение для клиента — сузить период; для L3 — повод оптимизировать запрос, если медленно и при нормальных фильтрах.

## Шум: ошибки, которые не про жалобу

На странице может быть красная строка, не связанная с проблемой: не загрузилась аватарка (`404`), не ответил виджет чата. Всегда спрашивай себя: **этот запрос объясняет то, на что жалуется клиент?** Аватарка не объясняет 9 секунд ожидания таблицы.

## Как это выглядит в тикете

> `POST /api/v2/orders/search` — 8.4 с, из них TTFB 8.3 с (ожидание сервера). В Payload `created_from: 2021-01-01` — поиск за 5 лет. Сервер вернул warning о медленном запросе. Клиенту предложили сузить период; если с периодом 30 дней тоже > 2 с — эскалация в L3.

## 🧭 В тренажёре

Открой страницу заказов клиента: найди самый долгий запрос, посмотри его Timing, Payload и Response.

## 🇬🇧 English corner

- *The page is loading forever.* — Страница грузится бесконечно.
- *It takes about 10 seconds to load.* — Загружается примерно 10 секунд.
- *Could you try a shorter date range?* — Попробуйте, пожалуйста, более короткий период.
- *slow query* — медленный запрос к базе; *date range* — диапазон дат.
- *Waiting for server response* — ожидание ответа сервера (TTFB).
