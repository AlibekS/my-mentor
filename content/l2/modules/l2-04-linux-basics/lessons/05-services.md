# Сервисы: systemctl status и journalctl (только смотрим)

Сайт магазина — это не одна программа, а несколько **сервисов**: веб-сервер `nginx` принимает запросы, приложение `shop-api` считает корзину и оплату, база данных хранит заказы. Если один сервис «упал», клиенты видят ошибку. L2 должен уметь **проверить**, работает ли сервис, и **прочитать**, почему он упал. Чинить и перезапускать — задача L3 (или твоя, но только по runbook).

## Что такое сервис

**Сервис** (service, daemon) — программа, которая работает в фоне постоянно: ждёт запросов и отвечает. В современных Linux сервисами управляет **systemd**, а команда для этого — `systemctl`.

## systemctl status — работает ли сервис

```
$ systemctl status nginx
● nginx.service - A high performance web server
     Loaded: loaded (/lib/systemd/system/nginx.service; enabled; preset: enabled)
     Active: active (running) since Sat 2026-11-01 08:00:00 +05
   Main PID: 1101 (nginx)

Nov 01 08:00:00 shop-web-01 nginx[1101]: Started nginx.
```

На что смотреть:

| Строка | Что значит |
|---|---|
| `●` зелёная точка / `×` красный крестик | быстро видно: работает или нет |
| `Loaded: … enabled` | сервис включён в **автозапуск** (стартует сам после перезагрузки) |
| `Active: active (running)` | **работает** |
| `Active: inactive (dead)` | остановлен (кто-то выключил или не запускал) |
| `Active: failed` | **упал** с ошибкой |
| строки внизу | последние записи журнала сервиса |

## systemctl --failed — кто упал

Не знаешь, какой сервис сломан? Покажи все упавшие сразу:

```
$ systemctl --failed
  UNIT               LOAD   ACTIVE SUB    DESCRIPTION
● shop-api.service   loaded failed failed Shop API
```

Список всех сервисов — `systemctl list-units --type=service`.

## journalctl -u — журнал сервиса

Сервисы пишут свои сообщения в общий журнал systemd. Читает его `journalctl`, а флаг `-u` (unit) оставляет только нужный сервис:

```
journalctl -u shop-api            # весь журнал сервиса shop-api
journalctl -u shop-api -n 20      # последние 20 строк
journalctl -u shop-api --since "09:40"   # с 09:40
```

Формат строки журнала:

```
Nov 04 08:15:12 shop-web-01 shop-api[2210]: Error: connect ECONNREFUSED 10.0.3.20:5432
дата и время    сервер      сервис[PID]     сообщение
```

Ищи строки с `Error`, `FATAL`, `Failed` — обычно причина записана прямо перед строкой `Failed with result`.

## Почему L2 не перезапускает «на всякий случай»

Перезапуск (`sudo systemctl restart …`) может:
- стереть следы проблемы, которые нужны L3 для поиска **первопричины** (root cause);
- не помочь, если причина — в базе данных или в настройках;
- задеть других клиентов, если сервис общий.

Поэтому порядок такой: **проверил статус → прочитал журнал → записал время и ошибку → эскалировал** (или сделал шаг из runbook, если он есть).

## Частые ошибки

- Смотреть только на `Loaded: enabled` и думать, что всё работает. `enabled` — это про автозапуск, а «работает или нет» — в строке `Active`.
- Читать журнал всех сервисов сразу без `-u` — утонешь в чужих сообщениях.
- Не записать **время** падения. Без времени L3 не свяжет падение с деплоем или другими событиями.

## Как это выглядит в тикете

«Клиенты не могут оформить заказ». Ты проверяешь `systemctl status shop-api` → `failed`. Читаешь `journalctl -u shop-api -n 20` → `Error: connect ECONNREFUSED 10.0.3.20:5432`. В эскалации пишешь: «shop-web-01: shop-api в статусе failed с 09:47 (время сервера), в журнале — не может подключиться к базе данных 10.0.3.20:5432. Ничего не перезапускал».

## 🇬🇧 English corner

- *The service is down / failed.* — Сервис упал.
- *active (running)* — работает; *inactive (dead)* — остановлен.
- *connection refused* — в соединении отказано (на том адресе никто не принимает подключения).
- *could not connect to the database* — не удалось подключиться к базе данных.
- *I haven't restarted anything.* — Я ничего не перезапускал.
